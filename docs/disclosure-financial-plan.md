# 原始披露与结构化财务落地方案

制定日期：2026-10-20。范围：当前 LLM_research 工作区中的 A 股公司研究。

实施进度：第一交付包的接口合同、源版本模型、权限检查及十家公司试点已完成，见[第一交付包记录](financial-contracts-delivery.md)。第二交付包已完成手动上传、官方链接归档、分类与修订管理、页级阅读，见[原始披露归档记录](disclosure-archive-delivery.md)。第三交付包已完成普通接口五年财务采集、标准事实、单季与 TTM、缺失原因、版本及历史截止日查询，十家公司已完成真实数据验证，见[标准财务交付记录](financial-series-delivery.md)。公告自动采集及 VIP 真实样本验证仍待相应权限开通；下文保留完整建设方案。

建议先完成“重点公司原始披露归档、五年财务序列、数字溯源、同业比较、修订跟踪”。Tushare 提供公告发现和结构化财务，原始文件负责证据核对，项目保存版本并计算指标。权限升级后扩大同步范围，沿用相同的数据合同和研究界面。

以下为原建设方案；接口条件已对照 Tushare 官方文档。已交付部分以各交付记录中的实际文件、表结构、接口和测量结果为准；其他表名、文件名、接口名和工时仍为拟议设计。

当前安排：第四交付包已恢复并完成，见[财务与研究证据连接交付记录](financial-research-delivery.md)。公司数字可连接原文页并保存独立依据，同业比较、研究回合冻结、修订影响复核、分享和 PDF 已接入。现有[工作台快捷命令](workbench-shortcuts.md)沿用同一能力入口。第五交付包的批量抽样和扩围另行实施。

## 1 首版交付范围

先选 10 家公司完成试点，再扩到项目关联公司和观察池中的 50–100 家。首版默认提供一般工商业公司的分析指标；银行、保险、证券可以归档原文和原始财务，但使用独立模板，通用毛利率、营运资本等指标显示不适用。

时间范围为最近五个完整会计年度加当年已披露期间。以本方案日期为例，主展示范围是 2021–2025 年和 2026 年已披露报表；为计算同比、TTM 和期初平均余额，再向前获取必要的比较基期。覆盖范围根据真实返回记录显示，未上市期间不算缺报。

首版用户能完成五件事：

1. 在公司研究页找到年报、半年报、季报、修订公告及相关审计报告，打开原 PDF 并定位物理页。
2. 查看核心财务的年度、累计、单季和 TTM 序列；缺数、口径变化和无法计算有具体原因。
3. 点击数字看到 Tushare 原始记录、单位、时间、版本、公式输入，以及已经核验的原文页。
4. 用统一口径比较 3–5 家公司，答案引用冻结的数据和原文。
5. 发现新财报、财务修订与数据冲突，进入现有资料变化检查和人工复核流程。

首版的直接产出是财务事实和可复算指标。业绩预告、快报、主营构成放在基础流程通过后接入；盈利预测、估值模型、全市场基本面选股另立后续验收。

## 2 现有项目的复用位置

当前已有可用基础：

- `apps/api/app/tushare_client.py`：直连官方 HTTP API、服务端凭据、超时与部分重试。
- `apps/api/app/research_tools.py`：研究侧已允许查询三表、财务指标、预告和快报，并保存当次响应；尚未形成跨会话共用的标准财务库。
- `apps/api/app/documents.py`、`report_parser.py`：PDF 哈希快照、页级文本、pypdf/Docling 解析和原文件完整性校验。
- `apps/api/app/jobs.py`、`worker.py`：任务租约、后台执行、进度和取消；当前 `tushare_sync.py` 的主同步阶段只有行情和资讯。
- `company_research.py`、`research_matrices.py`、`research_tracking.py`：公司资料、同业比较、资料变化及保存判断的复核。
- `storage.py`、`db.py`：可写存储与应用源码分离，以及按用户工作空间隔离数据库和证据文件。

需要一并调整的连接点：

- 当前原文证据类型主要是 `report` / `news`，`company_research.py` 还有“非 report 即 news”的分派。加入披露类型时必须改为明确分派，未知类型报错。
- 当前 `research_materials.py` 在最近有限数量的研报和资讯中抽取内容。财报研究要按公司、报告期、文档类型和章节选择材料，避免“五年对比”实际上只读取最近几份资料。
- `research_workspace.py` 的研究快照目前以研报、资讯和行情为主，需要增加本轮实际使用的财务版本和披露文件清单。

## 3 Tushare 接入清单与权限策略

### 原始披露

`anns_d` 用于发现公告并取得 PDF URL。官方文档说明该接口需单独开通公告数据权限，不能把财务积分升级理解为同时获得公告权限。接口单次最多 2000 条；首版按公司和公告时间窗口切分，遇到上限继续拆分。只有取得索引不代表 PDF 已下载或正文已解析。[公告接口文档](https://tushare.pro/document/2?doc_id=176)

原始文件优先归档定期报告全文、修订或更正文件、审计报告。业绩预告和快报原文可提前归档，但其数字不进入正式三表序列。摘要与全文分别标识；附注作为报告章节检索，不把报告摘要当成附注的替代资料。

`disclosure_date` 用于安排检查和发现应补资料。它的 `end_date` 是报告期，预计披露日不等于文件已公开；实际披露日也不能单独证明某一个 PDF 修订版本在当时已经存在。[披露计划文档](https://tushare.pro/document/2?doc_id=162)

公告权限未开通时，先支持用户上传原始 PDF 或导入官方原文 URL，补齐公司、报告期和发布日期。复用同一套存储、解析、证据和研究界面；公告自动发现状态明确显示“权限未开通”。

### 结构化财务

首批接入 `income`、`balancesheet`、`cashflow`、`fina_indicator`，随后加入 `fina_audit`。官方文档列出的普通财务接口门槛为 2000 积分；三表和财务指标的 VIP 接口支持按报告期获取多家公司数据，文档列出的门槛为 5000 积分。权限升级时优先启用批量采集路径，返回数据归入同一标准模型。[利润表](https://tushare.pro/document/2?doc_id=33)、[资产负债表](https://tushare.pro/document/2?doc_id=36)、[现金流量表](https://tushare.pro/document/2?doc_id=44)、[财务指标](https://tushare.pro/document/2?doc_id=79)、[审计意见](https://tushare.pro/document/2?doc_id=80)

第二批接入：

- `forecast` / `express`：单独展示预告区间、快报和正式结果的差异；保留各自发布版本，不互相覆盖。预告净利润上下限的原始单位是万元，必须按字段字典转换。[业绩预告](https://tushare.pro/document/2?doc_id=45)、[业绩快报](https://tushare.pro/document/2?doc_id=46)
- `fina_mainbz`：按产品、地区等维度展示主营构成。官方返回字段未提供公告日期，不能用报告期末充当公开时间；历史研究要关联可核验的披露版本，缺少对应证据时仅供最新口径查看。[主营业务构成](https://tushare.pro/document/2?doc_id=81)

新增接口描述注册表，逐项定义参数、日期含义、响应字段、单位、分片方式和权限状态。当前通用参数白名单不能直接覆盖所有接口；例如 `f_ann_date`、`comp_type`、`is_calc`、`pre_date`、`actual_date` 需要按对应接口开放。

权限检测执行有界样本请求，保存 `available / denied / rate_limited / transient_error / unknown` 及检测时间。空结果只能说明该样本无返回，不能判定整项权限或全市场覆盖。采集模式为单公司或按报告期批量；VIP 失败仅在确认普通接口可用时降级，并明确显示实际范围。请求频次从配置和实测获得，不写死一个全接口通用频率。

## 4 数据如何落地

保留现有 FastAPI、SQLite、文件快照、后台 worker 和 React。首版财务与披露数据位于当前用户工作空间，同一用户的多个研究项目引用同一份材料。通过 `application_paths()` 定位存储，延续现有授权和备份逻辑。全市场扩容时再评估独立、只读的公共数据仓库。

数据按以下顺序进入系统：

**接口响应或原始文件 → 不可变原始快照 → 带版本的标准事实 → 公式计算 → 公司页、研究工具与引用 → 新披露或修订复核。**

建议新增以下逻辑表；可以分两次迁移落地，具体迁移编号按实施时仓库顺序分配。

- `disclosures`：逻辑公告。保存证券、标题、类型、报告期、来源机构、发现渠道、原 URL、逻辑关联和归属确认状态。
- `disclosure_versions`：公告文件版本。关联已有 `documents.id`，保存内容哈希、公开时间及依据、抓取时间、替代关系和解析状态。相同 URL 内容变化产生新版本；同一 PDF 哈希复用已有解析结果。
- `financial_source_records`：源记录版本。保存接口、证券、报告期、报告类型、合并范围、公司类型、公告日期、实际公告日期、更新标志、原始行 JSON、规范化行哈希、响应文件哈希、抓取时间及历史可得性状态。整页响应也作为不可变文件保存。
- `financial_facts`：标准指标长表。每项保存 `record_id`、`metric_code`、维度、原值、原单位、标准值、标准单位、币种、缺失状态和映射版本。首版只开放经过核验的字段；源记录保留其余返回字段。
- `financial_evidence_links`：财务事实与原文的关联。保存披露版本、物理页、原文片段、表格行列或坐标、核对状态、核对方法和独立复核记录。
- `data_sync_runs` / `data_sync_items`：复用现有 `jobs`，增加接口与公司或报告期分片的检查点、返回条数、覆盖状态、重试时间和错误分类。
- `provider_capabilities`：保存按凭据配置标识区分的接口可用状态和检测时间，绝不保存或展示 token 本文。

保存原始响应时保留 HTTP 响应正文及字段清单；数值从原始 JSON 解析为 Decimal，SQLite 保存十进制字符串，避免先用二进制浮点做精确金额运算；图表按展示精度转换。缺失值保留空值，不能补零。推导结果保留公式版本、输入事实 ID、运行参数和结果快照；初期按需计算，可复用现有成果文件机制。

逻辑记录键包含“证券、报告期、报表或记录类型、合并范围、相关维度”；内容哈希区分版本。不能只按 `证券 + 报告期` 覆盖。完全相同的内容复用版本，同时记录本次观察；不同内容追加版本。`update_flag` 是来源元数据，不是唯一的修订排序依据。

版本选择器先匹配期间、范围和报表类型，再按有证据的发布或修订顺序选择。不能单凭抓取顺序决定两条冲突记录谁更正确；同一次响应内出现无法排序的冲突时，返回待核对。字段映射升级、请求字段改变和源数据实际修订分别记录，避免把采集配置变化误报成公司更正财报。

## 5 财务口径与历史版本

### 时间规则

每份数据至少区分三个时间：数据所属报告期、该内容公开的时间、平台首次观察到该版本的时间；同时保留供应商原始日期字段和时间精度。

三表的 `start_date/end_date` 是公告日期筛选，财务指标和主营构成的同名参数是报告期筛选。服务层分别处理，查询后的可得性校验仍不可省略。

提供两个明确的读取模式：

- **最新口径**：选取当前可用的最新版本，同时显示原始报告期和修订标记。
- **截至某日可验证口径**：仅选择能证明该版本内容在截止日前可得的记录。通过当时已归档快照，或与明确历史披露版本完成数值核对，建立证明链；无法证明的记录标记缺证，不参加严格历史比较。

今天取得的 Tushare 历史行，即使 `ann_date` 较早，也不自动获得“当时可得”的资格。`f_ann_date` 和 `update_flag` 不足以还原全部修订历史。当前研究工具已返回 `historical_revision_verified=False`，新服务应落实这一边界。

只有日期而没有时间的公告，保留日精度；日终研究可按日截止处理，日内事件分析不猜时间。实际交易或回测若使用该数据，另行采用经验证的交易日历和可交易时点规则。

### 首批指标

基础事实先覆盖约 25–35 项，完整列表由首阶段字段字典冻结。主页面先展示收入、归母利润、扣非利润、经营现金流、应收账款、存货、货币资金、总资产、总负债和归母权益，再提供成本、费用、研发、资本支出等展开项。

首批字段映射示例：收入取 `income.revenue`，归母利润取 `income.n_income_attr_p`，扣非利润取 `fina_indicator.profit_dedt`，经营现金流取 `cashflow.n_cashflow_act`。字段字典还要规定单位、累计或时点属性、合并范围、适用公司类型和空值含义；不能仅凭字段名推断。

衍生指标采用确定性公式：

- 单季收入、利润或现金流：一季度直接取累计；二季度为半年累计减一季度累计；三季度为前三季度累计减半年累计；四季度为全年减前三季度累计。
- TTM 流量：上一完整年度 + 本年累计 − 上年同期累计。
- 资产、负债、现金和存货等时点值直接使用期末余额，不作累计差分或 TTM 求和。
- 毛利率由同口径收入与成本计算；收入增长率基期为零时不输出普通百分比，利润跨越正负时同时显示绝对变化和转盈亏状态。
- 现金转换指标首版采用经营现金流 / 合并净利润，明确分子分母范围；归母口径的比率若另行提供必须单独命名。零或非正利润时提示比率解释限制。
- ROE 等比率不做简单季度相减。供应商指标与平台推导指标分别标识，后者保留公式与平均余额口径。

所有差分和比较要求币种、合并范围、会计期间、累计属性及可比版本一致。报表类型中包含单季、母公司、调整和上年同期重述等情况，不能把返回多行当重复数据删除。比较期在新财报中被重述时，要记录这一可比基础，禁止默默拼接旧口径。

标准化后执行勾稽检查：总资产与负债加全部权益、合并净利润与归母利润加少数股东损益、现金及现金等价物期初与期末及净增加额。比较必须使用相同报表版本、范围和单位；原文精度决定容差。未通过时保留原始数据并标异常，禁止自动改数使其相等；勾稽通过也不等于完成原文核验。

### 原文核对

分两层交付：

1. 每个标准数字都能回溯源记录、单位、版本和计算输入。
2. 核心数字进一步关联到原 PDF 的物理页和表格位置，核对其数值、单位、期间与合并范围。

仅按“公司 + 报告期”找到一份年报，状态只能是 `document_related`。只有完成数值与口径核对才可标记 `value_verified`；找不到可靠页码就不伪造定位。LLM/OCR 可以提出候选单元格和关联，发布为已核验事实要通过确定性规则或人工复核。

不一致时记录 `conflict`，并排展示供应商值与披露值。对同一口径、同一版本，已核验原始披露作为修正依据，用户确认后形成新的规范化版本，保留旧值。先排查单位、报告类型和重述，不能机械地把所有差异判成供应商错误。

## 6 后台采集与运行

新增 `disclosure_sync` 与 `financial_sync` 任务，复用租约、任务面板、权限上下文、取消和重试。调度负责入队，API 请求不等待全量下载。

首次接入依次执行：

1. 权限与接口合同检查，读取 10 家试点数据，测量调用量、文件尺寸和耗时。
2. 拉取指定报告期的三表和指标；记录每个分片的预期范围及实际覆盖。
3. 建立公告目录，优先下载对应报告期的完整定期报告和修订文件。
4. 发布原始快照后解析，创建标准事实，执行数值与时间检查。
5. 对试点核心指标核对原文，达到验收条件后扩展到 50–100 家。

拟议更新安排：Asia/Shanghai 每日 07:30 和 21:30 检查重点公司新披露，并允许手动刷新；同步时回看最近 30 天公告，每周重新核对最近 8 个报告期，每月校验全部已跟踪历史。它们是实施阶段的默认配置，本方案未创建定时任务。更老的修订仍可能延迟发现，界面须显示最近核验时间。

按接口实现分片适配器，不假定所有接口支持 `offset/limit`。公告达到上限时拆日期和证券范围；财务记录按公司及报告期分片；VIP 按季度拉取后核对覆盖。分片无法进一步拆小且仍触及限制时标记不完整，不能宣布全量完成。

对同一服务端凭据做跨 worker 的统一限速，并配置端点预算。权限拒绝暂停该端点；限流延后；超时有界重试；其他端点继续。网络请求在数据库事务外执行，成功的原始页和记录在短事务中提交检查点；解析失败与下载失败分别保留，可单独重试。

PDF 下载复用 `public_sources.py` / `request_security.py` 的安全读取逻辑，校验重定向、文件签名、大小和哈希，防止登录页或错误页被当成 PDF。大年报采用单独的可配置下载限额。Docling/OCR 按需启用，保留解析器版本和未识别页；避免每次读取都重新解析。

## 7 研究工具和产品如何接入

### 公司页和资料库

在现有公司研究页增加“财务”“原始披露”两个内容区，保留研究截至日期。财务区展示趋势、报告期和口径选择；数字侧栏提供源记录、公式和原文。原始披露区按报告期、类型、全文或摘要、修订状态过滤。

资料库增加“原始披露”分类。复用 PDF 阅读器和页定位组件，显示发布机构与发现渠道，避免把公司公告标为券商研报。

数据与服务增加公告、三表、指标、审计意见的独立状态，展示公司覆盖、报告期覆盖、最近同步、缺失原因和历史版本可验证程度。已下载、已解析、已核对是不同进度。

### 后端接口

拟新增：

- `GET /api/v1/companies/{code}/disclosures`：按报告期、类型、截止日和游标列出披露。
- `GET /api/v1/companies/{code}/financials`：接受指标、报告期范围、年度或单季等基准、合并范围、截止日和版本模式。
- `GET /api/v1/financial-facts/{id}/provenance`：读取源行、原始响应、公式输入及原文核对记录。
- `POST /api/v1/data-syncs`：提交明确公司及时间范围的采集；通过现有任务接口查看进度、取消与重试。

所有接口使用现有工作空间身份。财务接口统一返回值、单位、报告期、口径、版本、公开时间依据、覆盖状态、缺失原因和证据 ID；响应不以空数组掩盖权限错误。

### Agent 工具

新增 `search_disclosures`、`read_disclosure`、`get_company_financials`、`read_financial_evidence`、`compare_company_financials`。计算、口径对齐和历史版本选择由服务完成；模型负责选择问题、解释变化和读取附注。

研究默认读取标准库。库中缺数据时返回缺口和可补采范围，由现有任务流程补采；保留 `query_tushare` 用于探索性查询，原始探索结果仍需标准化后才能成为可复用财务事实。

原文引用保留现有字符与页定位；数值引用使用独立结构，保存 `fact_id`、源记录版本、计算结果版本和输入事实 ID。现有 `report/news` 引用继续可读；新增 `disclosure/financial` 类型时同步修改后端验证、前端来源阅读、分享快照和导出。数值来源不强行伪装为一段文字引用。

同业比较中的标准指标由服务计算，定性问题才交给模型读取相关章节。每轮研究冻结实际使用的数据版本和原文哈希；后续数据修订不会重写历史回答。资料变化检查增加“新报告、源数值修订、派生指标变化、来源冲突”事件，并列出受影响的旧判断，用户保存复核意见。

## 8 开发切分和验收

按五个可独立验收的交付包实施。以下工时为一名熟悉现有代码的工程师的初步净开发估算，包含针对性测试，不含权限等待、人工核对全部公司和历史数据长时间下载；10 家试点后修正。

### 交付包一 数据合同与权限检查 2–3 人日

新增 `tushare_endpoints.py`、`financial_contracts.py`，扩展 `tushare_client.py` 的错误分类和统一限速，补充接口状态。

交付：字段字典、端点参数与日期合同、当前可用能力、10 家试点清单和样本快照。

验收：权限拒绝、空结果、限流、网络失败可区分；三表与指标日期参数不会混用；普通和 VIP 返回可以映射到同一合同。人工导入可作为无权限时的试点入口。

### 交付包二 原始披露归档 4–6 人日

新增 `disclosures.py`、`disclosure_sync.py` 及披露迁移；从 `documents.py` 抽取共用 PDF 导入流程，扩展 `storage.py`、worker 和资料阅读组件。

交付：按公司查公告、下载原文、识别报告期与文档类型、保存修订关系、PDF 页级阅读。

验收：同文件重复导入不重复解析；同 URL 新内容保存新版本；公司及报告期不明确的材料进入待核对；全文和摘要不混淆；下载或解析失败可独立恢复。试点至少覆盖一组原报告与更正材料。

### 交付包三 标准财务和指标计算 4–6 人日

新增 `financial_store.py`、`financial_sync.py`、`financial_metrics.py`、`financial_api.py` 及财务迁移；加入三表和指标源记录、事实、检查点和公式快照。

交付：五年核心序列、年度和单季切换、单位转换、缺数原因、修订保留、严格历史模式。

验收：累计拆单季、TTM、时点指标和零基期用独立算例验证；原始与修订数据都可读；严格历史查询排除未获证实的后来修订；断点重跑结果一致；供应商缺字段不会变成零。

### 交付包四 公司页与研究证据连接 3–5 人日

新增 `CompanyFinancialsPanel.tsx`、`CompanyDisclosuresPanel.tsx`，扩展现有公司页、来源阅读器、资料快照、研究工具、同业比较和变化检查。

交付：点击数字查看源记录与原文、3–5 公司对比、研究回答中的数字引用、新披露影响检查。

验收：引用可离开原对话独立核对；重新同步后旧研究仍能读取当时版本；报告期和单位一致；财报目标章节能被检索，未被最近资讯挤掉；工作空间之间不能读取彼此资料。

### 交付包五 真实样本验收与扩容 2–3 人日

扩展现有 `benchmark_research_quality.py` 的冻结题库，加入三表、修订、缺失、单位和公司对比样本；完善备份、恢复和数据覆盖检查，再接入审计意见。通过后扩至 50–100 家，并安排预告、快报和主营构成的下一批接入。

交付：差异清单、人工核对记录、覆盖报告和真实运行耗时。

验收：满足下方首版完成标准。首版总体估算约 15–23 人日；通过交付包二即可先使用原始披露库，无需等待全部功能。

## 9 首版完成标准

固定 10 家试点公司，其中一般工商业至少 7 家，另含银行、保险、证券各 1 家验证适用性边界；修订、亏损、单位差异和缺报情况可在这些公司中交叉覆盖。发布时再验收所选 50–100 家的实际覆盖。

1. **覆盖可核对**：对试点范围逐公司逐报告期登记应有报告、实际文件、结构化记录及缺失原因。计划中的报告、权限受限、未返回和确认未披露分别统计。
2. **数字可追溯**：已展示事实全部可追溯到具体源记录及版本；推导指标全部保存公式和输入。不能把尚未核对的 PDF 关联标成数值已核验。
3. **核心数值抽检通过**：一般工商业样本每家至少核对两个年度与一个中期或季度的收入、归母利润、经营现金流、总资产、总负债；金融样本核对适用的核心项目。差异按原文展示精度和单位确定容差，未解释差异保留冲突状态。
4. **历史与修订正确**：用真实更正材料和明确标记的合成边界样本验证：更正前查询不出现后来版本；更正后可读到两者；历史可得性不足会返回缺证。
5. **计算正确**：人工或独立公式核对单季、TTM、负值、零分母、缺期、跨币种、合并范围及金融企业不适用情形。
6. **任务可恢复**：在下载、解析、写库阶段注入中断、限流和权限失败；重跑不重复、不漏分片，取消后不继续发布结果。
7. **研究有效**：至少完成五个端到端问题，包括利润与现金流背离、应收及存货变化、同业对比、历史截止日研究和修订影响。人工评分检查结论与证据是否相符，自动结构检查不代替语义验收。
8. **日常可用**：试点本机环境下，单公司已缓存财务查询目标 P95 小于 1 秒，3–5 公司标准指标对比目标小于 3 秒，均不含模型生成和网络采集；性能以真实样本测量为准。备份恢复后原文、引用和计算输入仍可读取。

## 10 权限升级后的扩展

升级完成后先重新检测端点权限，再对同一试点运行普通接口与 VIP 接口，比较证券、报告期、类型、版本和数值的一致性。达到条件后批量回填，保留原检查点和历史引用。

普通财务权限支持重点公司逐家获取；VIP 提高批量获取效率；公告数据权限决定能否自动发现并获取公告链接。这三项在数据与服务中分别呈现。主营构成及原文表格的逐字段核验可以逐步扩大，不因增加返回条数就自动标记已验证。

权限升级不会自行补齐历史修订证明，也不会补出原文未披露的业务指标。扩容优先级是当前项目与观察池、同业比较新增公司、其他研究对象。全市场筛选接入需要另行冻结证券范围、财务时点、复权和数据版本，届时再完成对应验收。
