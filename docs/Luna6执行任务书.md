## 1. 使用方法

在 Codex 中选择 GPT-6 Luna 后，复制下方“首次开工”内容。gpt-6-luna 是已核实的模型标识；模型由所用开发工具选择，不能通过修改应用的 config.ini 来切换当前开发模型。

推荐先完成 M1（L00—L09），得到可以实际使用的技术条件对话筛选闭环，再按 M2—M5 推进。整个项目仍以全部24个包为完整交付范围；只完成 M1 不等于整个项目完成。

如果希望一次授权执行完整计划，将首次提示词中的“本次授权连续推进M1，即L00—L09”替换为“本次授权连续推进完整计划L00—L23，按里程碑登记证据并持续继续”。上下文不足时通过进度表接续，不需要重新设计方案。

每次让执行模型读取进度表和当前工作包。主计划是设计事实源，进度表是完成状态事实源。不要把一段新聊天摘要当作已完成代码的证据。

默认使用单一开发模型顺序推进。没有必要为各库创建多个开发 Agent，也不要为了完成某个工作包擅自换模型。

## 4. 上下文管理

每次开始只装载以下最小上下文：

1. 用户最新补充。
2. 进度表的“当前接续点”和当前包。
3. 主计划的相关合同及该工作包。
4. 直接相关源文件与测试。
5. 上一个依赖包的接口和证据。

首次读完整体边界后，不需要每轮重新读取全部旧文档、回测项目和全部源码。需要跨包修改时，记录受影响接口并补充对应验证。

一个工作包如超出单次上下文，可以分成Lxx.a/Lxx.b；每个子包写清中间状态、尚未接通部分和下一步。原工作包只有整体行为和验收都通过才标记DONE。

## 6. 停止和继续的规则

- 代码编译或业务测试失败：修复当前实现并重新验证，不能改测试预期迎合错误。
- 外部服务、本地Python依赖、模型权限或生产数据缺失：登记BLOCKED_EXTERNAL或CODE_READY，继续可独立的包。Docker不是依赖。
- 上游仅真实环境待验但接口和离线测试通过：可以继续下游受控接线，不得因此启用尚未验证的生产能力或把依赖实测的包标为DONE。
- 对输入输出合同作兼容扩展：记录变化及测试，自主继续；不能把常规选择都变成用户确认。
- 需要改变用户业务目标、扩大外部数据范围或修改已确认筛选含义：说明具体分歧，保留可检查结果，不擅自改变。
- 用户明确改变范围：以最新要求为准，同步计划和进度。
- 当前授权范围完成：交付事实与下一阶段入口，不把未授权阶段写成已完成。

## 7. 针对本项目的常见误区

| 误区 | 正确处理 |
| --- | --- |
| 把旧文档的“不允许Python”当成本轮总限制 | 新算法使用已验收的本地Python子进程；旧资产继续兼容 |
| 把多次工具调用理解成策略优化 | 同一任务可以读取、计算、分析；不能改口径寻找更好结果 |
| 看到0命中就自动改阈值 | 0命中可以是正确结果，按原条件交付 |
| 看到GPT-6 Luna就覆盖应用模型设置 | 开发模型和应用模型分开 |
| 普通JSON响应成功就认为工具调用可用 | 单独验证call_id、工具输出和严格schema往返 |
| 给研报引用找到了原文就认为结论正确 | 继续核对主体、期间、事实/预测和支持关系 |
| 新功能保存到浏览器就算持久化 | 服务端保存会话、修订、运行和引用 |
| 为完成架构而整体重写代码 | 按工作包增量接线，保留已验证功能 |
| 把本地资讯导入说成实时资讯接入 | 分别说明数据来源和覆盖边界 |
| 把独立进程说成容器级隔离 | 本地进程负责超时、取消和资源监测，按本机用户权限运行 |
