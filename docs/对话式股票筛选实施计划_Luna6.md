## 1. 已确定的产品边界

### 1.1 必须实现

- 面向无技术背景用户，通过多轮对话提出、解释和修改筛选要求。
- 明确区分讨论、修改条件、执行筛选、解释历史结果、保存条件。
- 一段话可以包含多个库的条件，保留全部意图及且、或、排除、括号关系。
- LLM 可以选择已开放的数据、算法和工具，编写新计算程序，组织研报和资讯分析。
- 平台拥有数据接口、执行环境、输入输出合同、权限和资源限制、持久化、结果核验。
- 已确认的条件可保存、复用、组合；再次执行不会自行重新定义算法和阈值。
- 每次运行绑定条件、股票池、数据范围、截止时间和执行版本；逐股保留判断及依据。
- 缺失资料、语义不确定、执行失败、未处理都必须可区分。
- 用户可以追问某次结果，回答引用该次运行的数值、原文和条件版本。

### 1.2 明确不做

- 回测、收益率目标、参数寻优、策略进化、自动寻找更多命中、自动放宽条件。
- 交易执行、券商连接、下单及账户管理。
- 每一种筛选条件建立一个独立常驻 Agent。
- 以继续增加公式节点、指标名称或逐个数值函数白名单作为新算法的主要扩展方式。
- 根据用户未明确要求的目标，自动重新生成代码或重复运行筛选。
- 本轮直接采购、安装或接入未经选择的外部资讯、财务或行业供应商。
- 一次重建整个项目，或者从急速回测项目复制完整回测引擎和研究治理流程。

### 1.3 菜单与命名

保留当前六个一级入口：观察池、资讯库、技术指标库、形态库、研报库、组合选股。

本轮讨论中的“策略库”对应组合选股内保存的筛选组合和条件引用；不另建回测策略系统，不贸然新增第七个菜单。内部已有 strategies 表及策略版本继续复用。形态库原有手绘、OHLC、截图、模板和匹配能力必须保持可用。

资料库决定默认阅读上下文，不限制用户表达范围。在研报库提出技术加研报条件时，应生成跨库任务，并展示各条件来源；不能再要求用户拆成多个页面重新输入。

## 3. 总体架构及所有权

~~~mermaid
flowchart TD
    U["用户与各库页面"] --> C["持久会话与意图处理"]
    C --> T["版本化筛选任务"]
    C <--> A["一个公共 LLM 工具调用执行器"]
    A <--> R["能力目录与工具分派"]
    R --> D["行情 / 研报 / 资讯 / 形态 / 已保存条件"]
    R --> P["本地 Python 子进程计算"]
    R --> E["证据评估与引用核验"]
    T --> J["现有 jobs / worker"]
    J --> R
    R --> V["结果合同校验"]
    V --> S["不可变运行与逐股依据"]
    S --> U
    S --> X["引用本次结果的解释"]
    X --> U
~~~

### 3.1 平台负责

- 管理任务、修订、执行授权、运行状态、数据与条件版本。
- 执行工具，提供受控数据，实际计算、读取及保存产物。
- 检查结果形状、证券范围、时间、单位、引用、覆盖计数及版本一致性。
- 生成实际执行记录与统计；模型不能自行声明“已执行成功”代替工具事实。
- 控制超时、内存、取消、预算和异常；所有终态结果在有效租约下原子提交。

### 3.2 LLM 负责

- 理解需求，指出关键歧义，提出可读的口径建议。
- 在允许的能力内选择检索、计算和分析方法。
- 生成条件定义、计算源码或语义判断口径。
- 对实际工具结果进行业务判断和解释，提交符合合同的结果。

LLM 无需理解数据库、worker 租约或容器内部实现，也不直接写业务数据库。库页面只消费任务、条件和结果合同，不解析算法源码。

### 3.3 一个执行器、多种适配器

采用一个公共会话与工具调用执行器，按上下文加载适用工具。采用 technical、report、news、pattern、composition 适配器；它们不是多个独立决策 Agent。

新计算程序使用本地已安装的 Python 与 NumPy。开放新算法无需新增指标 ID；新增外部数据或依赖库须通过正式接口和依赖配置接入。

新对话不调用内置指标计算工具，不生成公式树或其他筛选 DSL。系统向模型提供原始行情字段、截止日、历史长度、参数和逐股结果合同；模型按用户意图编写普通 Python，平台负责准备输入、本地子进程执行及核验输出。现有技术指标浏览页和旧条件资产保留兼容，不作为新条件的计算依赖。

### 3.4 不引入业务优化循环

一个任务可以有多次工具调用，例如先查询数据范围、再读取材料、再计算；这是完成同一次筛选所需的步骤。

用户确认后，语义、阈值、比较范围和算法版本固定。默认自动改写次数为零。编译错误、运行错误或语义校验失败形成明确失败记录；用户要求修改或重试后再建立新修订或新运行。不能通过自动换算法、删条件、改阈值来“修好”命中结果。

网络故障和 worker 中断可按现有规则重试相同冻结输入，必须幂等；这不允许改写业务逻辑。新增模型调用默认不做可能重复付费的隐式整轮重放。

## 4. 对话与交互合同

### 4.1 五类意图

| 意图 | 示例 | 允许发生的变化 |
| --- | --- | --- |
| discuss | “这个成交量口径是什么意思” | 回答说明，不修改任务、不创建筛选运行 |
| edit | “涨幅上限改成10%” | 新增任务修订，显示差异；不自动执行 |
| execute | “改成10%再筛一次” | 更新修订并按当前明确口径创建一次运行 |
| explain_run | “为什么这次没有选中600000” | 绑定指定运行及证券，读取已保存依据，不重新筛选 |
| save | “把这个保存成温和放量” | 保存条件或组合版本；不隐式运行 |

意图分类由模型提供结构化候选，服务端结合用户消息、界面动作、当前修订及待执行状态核验。模型返回的 execute 标签不能自行构成授权。明确按钮动作优先；自然语言执行意图须保留对应用户消息和原文依据。矛盾或指代不明时只提出必要澄清。

### 4.2 澄清与执行

- 明确要求执行、口径完整、数据和执行能力满足：展示口径并直接执行，不额外要求重复确认。
- “最近”“明显增长”等会改变结果的歧义：集中提出关键问题，可给建议值；未经用户接受的建议不进入已确认口径。
- 已配置且可见的默认股票池、最新可用截止日可以复用，卡片显示实际采用值；不能把过期行情称为今天。
- 用户已请求执行但仍需澄清时，记录 pending_execute 及其用户消息；回答澄清后仅在任务范围没有扩张且意图仍有效时执行。
- “先不要运行”、新的讨论或取消必须撤销待执行意图。新增未确认条件使旧执行意图失效。
- “按这个筛”引用当前展示修订；如果页面已过期，返回版本冲突并刷新，不能执行另一个版本。
- 数据缺失不能靠对话猜测；可以保存明确的完整条件定义，但执行状态标记受阻。

### 4.3 任务修订

模型通过受类型约束的语义补丁修改任务，例如新增原子条件、改参数、替换组合树、修改范围；不使用任意数据库字段更新或路径注入。

补丁必须绑定 base_revision；服务端事务检查后生成新修订及中文差异。原子条件使用稳定 ID，同一条件重复引用用独立引用 ID，避免用户说“修改第二个均线条件”时改错对象。

用户原话、已确认口径和执行实现分别保存。不能让摘要替代原话，也不能让生成的中文说明与实际参数分离。

需求候选要逐条映射为条件、范围、排名、组合逻辑或待澄清项；服务端核对每段原文都被覆盖。修改必须声明目标条件ID或引用ID，并且新修订只能变更被本轮用户消息覆盖的目标字段。修改某个重复引用的参数时，参数覆盖和来源原文保存在该引用，不得改写共享条件定义。用户撤销运行时清除pending_execute；新增但未确认的筛选要求不能继续沿用旧执行授权。

### 4.4 页面

桌面页采用对话、当前条件卡片、结果三个关联区域；窄屏采用顺序区块或页签。保留各库阅读入口，在文档页发起对话时带入 document_id 和 page，不强制用户离开阅读页面。

聊天消息持久化；页面刷新、切库、服务重启后可以恢复。浏览器仅缓存界面偏好与草稿输入，不能成为条件版本或运行结果的唯一存储。

显示用户有意义的进度，如“已读取12份材料”“已判断420只”；技术日志、JSON、代码和 token 默认不进入用户主流程。代码及技术诊断放在可选详情。

## 5. 数据模型与接口合同

以下名称为目标设计；L01 固定精确字段。已有表能承载的字段优先扩展，不能同时建立两份独立权威条件库。

### 5.1 会话与任务

| 对象 | 必需信息 | 所有权与不变量 |
| --- | --- | --- |
| Conversation | id、入口库、标题、当前 task_revision、active_run_id、状态 | 一个会话可有多次运行；不因查看旧运行覆盖当前任务 |
| ConversationMessage | id、conversation_id、role、content、client_message_id、引用、时间 | 用户消息不可由模型改写；提交幂等 |
| ConversationTurn | id、message_id、base_revision、job_id、状态、错误 | 同一会话只允许一个修改任务的活动回合；重复请求返回同一回合 |
| ScreeningTaskRevision | task_id、revision、原子条件、逻辑树、范围、口径、未解决项 | 修订不可覆盖；未解决要求不能被静默省略 |
| ExecutionRequest | 用户消息或按钮来源、绑定修订、请求动作、幂等键 | 由应用服务创建；模型不能生成一个自称已授权的凭证 |
| ConditionImplementation | 条件版本、实现类型、参数、输入需求、产物引用、算法版本 | 实现变化必须形成新条件版本 |

任务范围至少包括证券名单或股票池引用、排名范围、截至时间、资料回溯窗口、价格口径、缺失处理和排名并列处理。逻辑树负责组合已有条件，不限制条件内部算法。

### 5.2 能力与工具

CapabilityManifest 至少包含 capability_id、version、description、input_schema、output_schema、available、unavailable_reason、fields、units、time_granularity、coverage、side_effect、resource_policy。

工具注册表是服务端实际可调用函数的投影。不能只在提示词中声称某项能力存在。

首批工具：

| 工具 | 输入重点 | 返回重点 |
| --- | --- | --- |
| describe_capabilities | 任务范围与所需领域 | 实际可用能力及缺失原因 |
| query_market | 股票池、字段、窗口、截止日 | 有身份的数据句柄、单位、质量与覆盖 |
| search_documents / read_document_pages | 来源集合、日期、查询、文档与页 | 可核验片段、来源 ID、覆盖状态 |
| search_news / read_news_items | 来源集合、日期、查询、资讯 ID | 原文、时间、关联证券、覆盖状态 |
| inspect_condition | 条件 ID 与版本 | 已保存口径、参数、实现及可用性 |
| compute_builtin | 数据句柄、算法 ID、参数 | 标准数值或逐股判断产物 |
| run_python_condition | 已封存代码产物、数据句柄、参数 | ConditionBatch 与执行记录 |
| evaluate_evidence | 判断口径、固定资料集合 | 逐证券判断、引用、覆盖与模型记录 |
| match_pattern | 模板版本、行情范围 | 相似度、分项差异和依据 |
| read_run_decisions | run_id、证券及条件引用 | 历史依据，只读 |
| propose_task_patch | base_revision、受约束补丁 | 验证后的新修订或明确错误 |
| request_screening | task_revision、真实 ExecutionRequest 引用 | 已排队 run_id，不等待子任务完成 |

所有数据句柄、artifact_id、执行 ID 由系统产生并绑定任务。来自另一任务的句柄不能随意访问。模型参数不能覆盖服务器注入的截止时间、权限或数据身份。

### 5.3 结果

ConditionDecision 至少包含：

- stock_code、condition_id、condition_version、reference_id。
- state：true、false 或 unknown。
- evaluation_status：completed、failed 或 not_evaluated。
- reason_code、用户可读说明、actual_values、thresholds、units。
- evidence_refs、artifact_refs、data_as_of、implementation_id。

completed 可以返回 unknown，例如缺少历史或证据冲突。failed 与 not_evaluated 的 state 必须为 unknown。条件级错误和股票级最终判断分别记录；AND 中一个明确 false 可以确定整体 false，但不能丢弃另一个条件未完成的覆盖信息。

RunResult 至少包含 run_id、task_revision、condition_snapshots、universe_snapshot、source_manifests、execution_version、status、counts、coverage、decision_refs、tool_call_refs、model_metadata。

计数必须由持久化逐股记录计算：

~~~text
target_total = true_count + false_count + unknown_count
unknown_count 包括对应股票最终无法判断的缺数据、语义不确定、失败、未处理。
失败/未处理与 unknown 的分项关系必须明确，界面不能重复相加。
条件级异常计数单独显示，不混充股票级数量。
~~~

即使任务取消，目标范围也不能缩成已完成子集；尚未处理的证券形成明确占位判断或等价可查询状态。只返回命中名单不满足合同。

## 6. 执行边界与关键语义

### 6.1 时间与输入

- 存储时间使用明确时区，用户展示 Asia/Shanghai；日线截止日采用实际数据日期。
- 明确区分“按最新可用行情筛选”和“截至今天”；数据滞后必须可见。
- 行情、研报、资讯各有水位，不能把较新的研报填入更早的截至日。
- 财务、行业、ST、分钟行情等未接入时，保留完整条件并报告能力缺失。
- 数据读取由 broker 按任务物化，只向计算程序提供本次允许的数据；不挂载整个项目或业务数据库。
- 输入规范包括股票、日期排序、缺失掩码、字段单位、价格口径和历史长度。
- 不把旧实现最多500根、一维单股输入当成新系统永恒限制；按需求和资源预算取实际可用数据。

### 6.2 排名和组合

全市场排名、观察池排名、行业内排名、过滤后排名必须在任务中显式区分。不能为了减少计算先过滤，再声称完成全市场排名。

每个排名节点声明 ranking_universe、rank_after_filters、direction、top_n 或 top_fraction、ties_policy、missing_policy。前百分比的取整及并列规则以卡片展示的约定为准；默认建议为向上取整及代码稳定打破并列，用户可修改。

严格排名所需数据不完整时，不自动把排名范围缩小。默认将依赖该排名的结果保留 unknown/partial；用户明确选择“只比较有数据的股票”后生成新口径。

普通且、或、排除继续使用现有三值逻辑；NOT unknown 仍为 unknown。新实现应调用统一组合器，避免各适配器自行定义不同语义。

### 6.3 开放 Python 计算

采用本地独立 Python 子进程，复用系统 Python 3.12 与项目依赖目录，无需 Docker 或镜像。当前计算库为 NumPy，算法可使用普通 Python 语法和标准库。

参考程序接口：

~~~python
def screen(context, frames, params):
    # context: 任务、截止时间、数据合同；不能修改
    # frames: 已按任务物化的表或数组
    # params: 已确认参数
    # 返回截止日的逐股判断和解释指标；预览时可返回有上限的诊断时序
    return {"decisions": {"600000.SH": True}, "metrics": {"600000.SH": {"score": 1.0}}, "units": {"score": "%"}}
~~~

允许常规 Python 函数、类和现有库内算法；资源约束放在运行环境，不用新的 Python 子语言替代标准运行时。模型不能在运行时安装依赖；确需新库时形成可审查的能力扩展。

每次运行使用独立临时工作目录、固定输入和有上限的输出通道；不向子进程转发模型密钥等应用环境变量。超时、取消、输出/内存/进程数超限时终止计算和已发现的派生子进程。独立进程用于运行控制，不提供容器级网络或文件系统访问隔离；它按本机用户权限运行。

初始限制：64 MiB输入、20 MiB输出、60秒墙钟、1 GiB进程树内存监测阈值、64进程；数值库默认2线程。资源监测是本地运行控制，不是操作系统强制配额。横截面计算必须保留完整比较范围，不能按分批局部排名。

语法/类型检查仍用于提供清楚错误和验证入口。不能把 AST 白名单、python -I 或普通子进程宣称为完整隔离。

本地 Python 或 NumPy 不可用时报告 runtime_unavailable；修复项目依赖后可直接执行。真实本地计算验收见 tests/integration/test_local_runtime.py，无容器验收要求。

### 6.4 研报与资讯

定义统一 EvidenceSource：source_type、source_id、证券映射、publication_at、available_at、原文定位和覆盖状态。研报以页定位，资讯以段落或字符区间定位。内容哈希及完整来源审计暂缓；正文和日期用于实际分析正确性。

模型自主选择检索词、相关材料和分析顺序；固定资料集合的身份、截止时间及已处理范围由系统记录。

相关性检索不等于穷尽评估。只查看命中片段时，不得声称已检查全部报告。大文档按页或段分块，记录未读取/截断范围；不能把当前 MAX_REPORT_CHARS 限制包装成完整阅读。

判断保存实际事实、公司表述、分析师观点、预测、反向证据等类型；“已实现增长”不能由预测代替。原文引用校验只能证明引用存在，还需核对主体、期间和支持关系。

存在条件、所有资料条件、明确反向事实条件必须区分量词和范围。没有提到不自动为 false。跨文档矛盾默认 unknown 并列出冲突；不得默认选最乐观的一篇。

复杂的来源哈希/模型/提示版本缓存链暂缓。当前不得只按同一句问题复用可能过期的分析；没有可靠的输入一致性依据时重新读取和分析。

资讯先支持用户输入/本地导入的真实文本及标准来源元数据，复用同一分析合同；实时供应商保持 disconnected，外部同步不属于本轮默认接入。没有资讯时可完成软件验收，但不能宣称真实实时资讯筛选完成。

### 6.5 模型调用

沿用当前 provider 配置，新工具流程优先走 Responses。旧 complete_json 调用保留兼容，避免一次改坏已有研报及形态生成。

按官方合同显式设置严格工具 schema，对象禁止额外字段，必填字段和可空字段分清。服务端仍做类型与业务校验；严格 JSON 不代表语义正确。

工具调用必须按 call_id 配对，保留本回合需要的 response items，并将真实 function_call_output 返回模型。按官方协议处理返回的非文本条目，不能只拼 output_text 后丢失工具或必要上下文。

连接测试分为普通文本、严格结构输出、只读工具调用往返三项。代理不支持时显示具体不兼容项；不能把一次普通 JSON 成功作为 Agent 全链路验收。

禁止模型调用 shell、任意 URL、任意文件路径、业务数据库写入或设置凭据。第三方文档及资讯只作为数据，其内容不能扩张工具权限。

初始每回合最多12次工具调用、120秒墙钟，耗时筛选另起持久任务；预算和时间可配置并记录。到限返回当前状态与未完成原因，不循环改提示直至“成功”。模型用量按实际响应记录；价格未配置时不伪造金额。

### 6.6 任务、取消和恢复

复用 jobs 和 worker，新增 conversation_turn 与 screening_v2 类型及协议。会话回合创建筛选任务后立即返回排队结果，不能让唯一 worker 阻塞等待自己创建的子任务。

筛选任务内部直接调用可复用证据服务，或使用明确的可恢复分阶段编排；不能同步等待一个只有当前 worker 才能领取的 report_evaluation 子任务。

新协议建议 screening-contract-v2。数据库触发器及 claim 支持列表同时升级，旧 worker 不能领取新任务，旧运行继续按旧协议读取。终态状态、结果和逐股依据必须同一事务完成；不能先写终态再被不可变触发器阻止写结果。

网络调用及大批计算期间续租；取消后返回的迟到模型输出、证据缓存和结果都要验证租约与任务状态，不能复活任务。手动重试创建新运行并引用原快照，相同重试请求幂等。

| C14 | “放量股票中的前10%” | 与C13可产生不同结果 |
| C15 | “行业内前10%”，行业数据未接入 | 完整保留要求，报告能力缺失 |
| C16 | 新回归/波动公式，内置目录没有 | 无需新增指标枚举，真实计算正确 |
| C17 | 数据不足、坏bar、除零 | unknown，不变成0或false |
| C18 | “排除数据不足的反向条件” | 明确未知处理，NOT unknown不变true |
| C19 | 要求已实现增长，报告只有预测 | 不以预测支持命中 |
| C20 | 一篇支持、一篇明确反向 | 显示冲突，按确认口径判断 |
| C21 | 提供了原文但主体/期间不符 | 不因引用存在自动支持结论 |
| C22 | 只检索到部分材料 | 不声称全库穷尽判断 |
| C23 | 回购计划与已完成回购 | 事件状态不混淆 |
| C24 | 多篇资讯转述同一事件 | 不冒充多条独立证据 |
| C25 | “这个条件是什么意思” | 只讨论，不改版本、不运行 |
| C26 | “保存这个条件” | 保存完整口径，不额外筛选 |
| C27 | 含未知要求和已支持要求的一句话 | 不静默忽略未知项或保存残缺意图 |
| C28 | 0只命中 | 不自动放宽阈值、不重生成程序 |
| C29 | 重复点击、刷新、取消后模型迟到 | 幂等、恢复、取消状态不被覆盖 |
| C30 | 保存后换日期重跑，再追问历史 | 实现版本稳定，旧结果不变化 |

另外保留安全与合同专项：越权工具、跨任务句柄、伪造执行ID、路径穿越、文档提示注入、未来数据、重复证券、输出形状错误、超时、资源耗尽和旧 worker。

真实模型验收应报告样本数、重复次数、通过率及失败例，不能用少数成功样例宣称通用自然语言准确率。关键错误包括静默丢条件、无授权执行、未来数据、伪造依据、未知变否定及自动改阈值，出现任一项即不通过交付门槛。

## 11. 里程碑及完成定义

| 里程碑 | 工作包 | 可展示结果 | 不可冒充的完成项 |
| --- | --- | --- | --- |
| M1 对话筛选闭环 | L00—L09 | 技术条件对话、澄清、修改、一次执行和持久恢复 | 尚不能宣称开放算法和全部资料库完成 |
| M2 开放计算 | L10—L12 | 新算法本地子进程执行、正确比较范围和排名 | mock不等于真实本地运行通过 |
| M3 资料与跨库 | L13—L17 | 研报、真实本地资讯、形态和技术统一组合 | 不把本地资讯称为实时资讯接入 |
| M4 复用与可靠性 | L18—L21 | 历史追问、版本复用、取消恢复和升级 | 不把旧结果重新计算成“兼容” |
| M5 验收交付 | L22—L23 | 真实模型、浏览器、完整回归和运行手册 | 不用构建成功代替产品验收 |

所有24个包必须有状态和证据。软件合同可完成但真实外部依赖待验时，应分别报告“工程完成”和“实际环境未验”，不能直接合并成全部完成。

不按固定天数承诺工期。先完成 L00—L09 测量实际开发与验证工作量，再更新后续工作量判断；不为节省时间删除验收或收窄用户已确认目标。

## 12. 发布、兼容与停止条件

采用增量迁移和显式新入口配置；默认保留历史记录可读。新实现编译、数据输入和终态提交共用单一入口，避免前端预览和后台筛选两套计算定义。

以下情况停止相关路径并报告，不自动降级：

- 无法保持用户已确认的条件含义或比较范围。
- 请求依赖自定义程序，但本地 Python 或 NumPy 不可用。
- 来源/证券/日期无法核验，结果依赖这些信息。
- worker 协议不兼容、数据在执行中改变、结果哈希不一致。
- 未经用户要求的条件放宽、算法重生成、绩效或命中数量优化。

这些条件不要求整个开发停工。可继续独立模块、离线合同验证和其他资料库接线。最终报告必须具体列出阻断、已验证范围和恢复条件。
